# Hinweise für Claude Code

## Prozess (unverhandelbar)

- Nach Abschluss einer Aufgabe auf einem Feature-Branch **immer direkt einen Pull Request erstellen** (nicht erst nachfragen oder darauf warten, dass der User explizit danach fragt). Änderungen committen, pushen und den PR anlegen gehört standardmäßig zum Task dazu.
  **Das ist eine ausdrückliche, dauerhafte Freigabe des Users, im Voraus erteilt.** Sie gilt für jede Session und jede Aufgabe in diesem Repo. Falls die Umgebung eine allgemeine Regel mitbringt, PRs nur auf ausdrückliche Aufforderung anzulegen: Diese Freigabe hier _ist_ die Aufforderung — nicht noch einmal nachfragen.
- **PRs NICHT mehr automatisch mergen.** Der User möchte Änderungen erst separat testen (z. B. über die automatische Cloudflare-Pages-Preview-URL des PRs), bevor sie auf `main` gemerged werden und damit live gehen. Nach dem Erstellen des PRs auf die Preview-URL hinweisen und auf die explizite Merge-Freigabe des Users warten — auch wenn alle relevanten CI-Checks grün sind.
- **Nach dem PR ist die Aufgabe zu Ende.** Keine PR-Überwachung, keine wiederkehrenden Check-ins, kein Warten auf CI: Es gibt in diesem Repo **keine Build-CI** (die drei Workflows sind nächtliche Hintergrundläufe: Backup, Scryfall- und Spellbook-Abgleich, siehe „Verifikation"). Ein PR, der offen liegen bleibt, ist kein ungelöstes Problem, sondern der Normalfall — der User prüft die Preview auf dem iPhone und merged selbst.

## Das Projekt in fünf Zeilen

Statsfinity ist eine deutschsprachige, **mobile-first** PWA (iPhone/Safari zuerst) rund um _Magic: The Gathering_ — Matches erfassen, Statistiken, Decks, Turniere.

- **Angular 21**, standalone components + Signals, keine NgModules, TypeScript strict + `strictTemplates`
- **Kein Angular Router** — die Navigation läuft über ein Signal (siehe unten)
- **Supabase** als Backend (Postgres, Auth, Realtime); Client in `src/app/supabase.client.ts` (der Anon-Key ist bewusst eingecheckt)
- **Cloudflare Pages** als Deployment, konfiguriert im Cloudflare-Dashboard (kein `wrangler.toml`, kein Deploy-Workflow im Repo)
- App-Sprachen: `de` und `en`. **Commits, PR-Titel und PR-Beschreibungen auf Deutsch.**

### Navigation — es gibt keine URLs

`src/app/navigation.service.ts` hält den aktiven Tab als Signal:

```ts
type AppTab = 'match' | 'search' | 'stats' | 'group' | 'profile';
```

Die Shell `src/app/app.ts` / `app.html` schaltet per `@if` zwischen rund 22 Komponenten um. **Es gibt keine Routen und keinen `RouterOutlet`.** Wer nach Routing sucht, sucht vergeblich.

**Eine einzige Ausnahme:** `?deck=<uuid>`. Ein QR-Code braucht eine Adresse, auf die er zeigen kann (siehe Steckbrief weiter unten), also wertet `NavigationService` beim Start genau diesen einen Parameter aus (`deckLinkLesen()`) und baut ihn (`deckLink()`). Das ist der **einzige** Ort im Projekt, der eine URL liest. Er schaltet auf den Suche-Tab und legt die Deck-ID in `pendingPublicDeckId` ab; `search-tab` springt daraufhin auf den Unter-Reiter Decks, `public-deck-browser` holt das Deck einzeln (`PublicDeckService.getPublicDeck()`) und öffnet es. Danach wird der Parameter per `history.replaceState` aus der Adresse genommen - sonst landet jedes Neuladen wieder in diesem Deck. Bewusst **kein** Router dafür: eine Routing-Tabelle für einen einzigen Parameter wäre ein Gerüst um eine Schraube herum.

### Wiederverwendbare UI-Bausteine — hier zuerst nachsehen

`src/app/ui/` enthält: `bar-chart`, `life-chart`, `radar-chart`, `meter`, `split-bar`, `pager`, `podium`, `overflow-menu`, `multi-select`, `color-filter`, `cmc-filter`, `mana-symbol`, `bracket-badge`, `rank-badge`, `icon`, `info-toggle` sowie `chart-scale.ts`.

`info-toggle` ist die Überschrift mit ⓘ-Knopf, der eine Erklärung aufklappt (`<app-info-toggle [label]="…"><h3 info-title>…</h3> Erklärtext </app-info-toggle>`). **Erklärtexte gehören dahinter, nicht als Dauertext auf die Karte** (Wunsch des Users, 05.10.2026) - sichtbar bleibt nur, was man zum Ablesen braucht.

`icon` ist der Piktogramm-Satz der App (`<app-icon name="trash" />`): ein gemeinsames 24er-Raster, eine Strichstärke, Farbe immer `currentColor`, Größe aus der `font-size` der Umgebung. **Er hat die Emojis abgelöst, die vorher überall in der Oberfläche standen** — die zeichnet jedes Betriebssystem anders, sie sind bunt und lassen sich weder einfärben noch in der Strichstärke angleichen. Ein neues Piktogramm gehört in `icon.html` (`@case`) **und** in die Union `IconName` in `icon.ts`; das eine ohne das andere kompiliert nicht bzw. zeichnet nichts. **Ein `<button>` um ein Icon herum muss eine eigene `color` setzen** — Knöpfe erben die Textfarbe nicht, sie nehmen die dunkle Browser-Standardfarbe, und das Piktogramm zeichnet in `currentColor`. Bei einem Emoji war das egal, hier wird der Knopf dadurch unsichtbar.

**Regel: bevor ein Diagramm, ein Filter, ein Menü oder eine Blätterfunktion neu gebaut wird, prüfen, ob es das hier schon gibt.**

### Weitere Orte

- **Typen:** `src/app/models.ts`, `src/app/tournament.models.ts`
- **Übersetzungen:** `src/app/i18n/` — 13 Module (`auth`, `common`, `deck`, `deck-view`, `feedback`, `group`, `ingame`, `match`, `profile`, `search`, `stats`, `tournament`, `tutorial`), je Datei beide Sprachen. Siehe die Arbeitsregel weiter unten.
- **Styles:** Design-Tokens (`--sp-*` Abstände, `--r-*` Rundungen, Flächen, Diagrammfarben) global in `src/styles.scss`; Partials in `src/styles/` (`_breakpoints.scss`, `_mana.scss`). Style-Budget: **6 kB Warnung / 12 kB Fehler pro Komponenten-Style** — große `.scss`-Dateien nicht unbegrenzt wachsen lassen.
- **Deck-Löschen ist ein „Grabstein", kein `delete`:** `DeckService.deleteDeck()` entfernt ein Deck nur dann wirklich, wenn **keine einzige Partie** daran hängt. Sonst werden `deck_cards` und `deck_change_log` gelöscht (das ist der Teil, der Platz kostet), die `decks`-Zeile bleibt mit `deleted_at`, gerettetem Commander und den **zählenden Kartennamen als `text[]`** stehen (`sql/deck-grabstein-loeschen-2026-09-21.sql`) — ein Array je Deck, keine Zeile je Karte, ohne Mengen und Bild-URLs (~1 kB statt ~21 kB), damit auch „Meistgespielte Karten" im Profil ein gelöschtes Deck nicht vergisst. Grund: `match_players.deck_id` ist `on delete set null` — ein hartes Löschen riss Deckname, Besitzer und Farbidentität aus jeder Partie und verschob die Spiele aus der Deck- in die Commander-Wertung. **Wer eine neue Deck-Abfrage schreibt, entscheidet bewusst:** Listen/Auswahl/öffentliche Suche filtern über `DeckService.nurLebende(query)`, Statistik-Abfragen (`getColorIdentities`, `getCardAndColorStats`, Namens-Joins in `mtg.service.ts`, die globalen SQL-Funktionen) dürfen **nicht** filtern — sonst ist der Verlust wieder da. Fehlt die Migration noch, schaltet sich der Filter beim ersten `42703` selbst ab (`grabsteinSpalteVerfuegbar`, gleiche Mechanik wie bei den Bracket-Spalten), und Decks mit Partien lassen sich solange nicht löschen, statt sie ungeschützt zu verlieren.
- **Postfach: keine Benachrichtigungstabelle, nur eine Gelesen-Liste:** `deck-comment-inbox.service.ts` + `comment-inbox/` zeigen Kommentare auf eigene Decks und Antworten auf eigene Kommentare, mit Zähler am Profil-Symbol der Tab-Leiste (`app.html`). **Gespeichert wird ausschließlich, was schon GELESEN wurde** (`deck_comment_reads`, `sql/deck-kommentar-postfach-2026-09-22.sql`) — ungelesen ist die *Abwesenheit* einer Zeile. Die Nachrichten selbst stehen bereits vollständig in `deck_comments`; eine zweite, per Trigger gefüllte Kopie könnte davon nur abweichen, und sie würde je Kommentar wachsen statt je Klick. **Der Zähler ist eine eigene Abfrage, nicht `entries().filter(...)`:** die Liste ist auf 50 begrenzt, ein Zähler daraus bliebe bei 50 stehen. Aus demselben Grund ruft `deck_comment_unread_count()` die Funktion `deck_comment_inbox()` auf, statt deren `where`-Bedingung ein zweites Mal hinzuschreiben — zwei Fassungen derselben Regel laufen auseinander (siehe die Sieg-Muster weiter unten). Eine Antwort auf den eigenen Kommentar unter dem eigenen Deck erfüllt beide Bedingungen und erscheint trotzdem **einmal**, als `reply` (ein `case`, kein `union`). Aufgefrischt wird beim Login und bei Rückkehr aus dem Hintergrund (`PageVisibilityService`), **kein Polling** — ein Hintergrund-Tab wird vom Browser ohnehin gedrosselt. Der Sprung aus dem Postfach ins Deck läuft über `DeckCommentService.highlightCommentId`, das **vor** `DeckViewerService.open()` gesetzt wird; die Kommentarliste lädt asynchron und greift es auf, sobald sie steht.
- **Aufrufe und Likes: ein Zähler und eine Like-Tabelle, beide NICHT an `decks`:** `deck-social.service.ts` + `deck-social/` (Auge mit Zahl, Herz mit Zahl) stehen in `deck-detail-view` und `public-deck-browser` unter dem Kopf und kompakt in jeder Zeile von `deck-list` (u. a. „Meine Decks" im Profil). Tabellen und Funktionen in `sql/deck-aufrufe-likes-2026-09-22.sql`. **Aufrufe sind ein Zähler je Deck (`deck_view_counts`), keine Zeile je Aufruf** — die würde mit jedem Öffnen wachsen, und niemand fragt, wer wann geschaut hat. Gezählt wird nur über `deck_register_view()` (SECURITY DEFINER, auch ohne Login): nicht der Besitzer, keine privaten Decks, keine Grabsteine; der Client zählt dasselbe Deck je Sitzung nur einmal. Likes (`deck_likes`, Primärschlüssel `(deck_id, user_id)`) nur eingeloggt und **nicht fürs eigene Deck**. Gelesen wird gebündelt über `deck_social_stats(ids[])` — die Deckliste fragt eine ganze Seite mit einer Anfrage ab. Dieselbe Funktion liefert auch den **Besitzernamen** (`owner_name`, **nur** der Profilname aus `profiles`, beim Lesen nachgeschlagen; SECURITY DEFINER wie bei den Kommentaren — Decks von Spielern ohne Login haben keinen). **Ein Tipp auf „von …“ öffnet das Profil des Besitzers** (`openOwnerProfile()` → `ProfileService.viewProfile()`, derselbe Weg wie „Profil ansehen“ im Gruppen-Tab) — auch ohne Login: `app.html` lässt den Profil-Tab durch, solange `viewingUserId()` gesetzt ist, und `loadPublicProfile()` fällt auf die SECURITY-DEFINER-Funktion `public_profile()` zurück (`sql/oeffentliches-profil-2026-09-23.sql`), weil `profiles` für `anon` gesperrt ist. **Die Match-Liste eines fremden Profils ist öffentlich** (Entscheidung des Users, 23.09.2026): Spielt der Besitzer nicht in der Gruppe des Betrachters (oder ist der gar nicht eingeloggt), kennt `mtg.history()` seine Partien nicht — dann lädt `profile-tab` sie über `MtgService.loadPublicMatchesForUser()` aus **allen** Gruppen (SECURITY DEFINER `public_player_matches()`, `sql/oeffentliche-matches-2026-09-23.sql`, jsonb im Zuschnitt von `MATCH_HISTORY_SELECT`, damit `mapMatchRow()` sie liest) und reicht sie als `externalMatches` an `player-match-history`. Nicht herausgegeben werden `group_id` sowie Name und ID privater Decks. Im öffentlichen Stöbern ist jede Kachel **ein** Rahmen (`public-deck-frame`) mit durch Linien getrennten Zeilen: Commander-Bild, Leiste (`public-deck-bar`: Aufrufe, Likes, bei zwei Commandern der Umschaltknopf, rechts Siege/Partien und Winrate), Deckname, „von …“. Umschalt- und Umdreh-Knopf (doppelseitige Commander) sitzen dort statt auf der Karte: `partner-card-image` hat dafür `showSwapButton`/`showFlipButton` sowie `frontIndex` und `frontShowingBack` als `model()` (durchgereicht an `card-image`, das `showFlipButton` und `showingBack` als `model()` hat), den Zustand je Deck halten `partnerFront` und `flipped` im Stöbern. **Ein Klick aufs Commander-Bild einer Kachel öffnet dort den Steckbrief als Popup** (`openPassport()`, eigener Zustand neben `selectedDeck`, eigene Kartenabfrage für Wirkungs-Kacheln und Ø Manawert), erst „Deck ansehen“ darin öffnet das Deck und zählt damit einen Aufruf. Lokal fehlt im Steckbrief-Bild das Artwork, weil `/api/proxy-image` eine Cloudflare-Funktion ist, die der Dev-Server nicht kennt. Die Zahlen liegen im Service je Deck-ID, damit ein Like in der Ansicht beim Zurückgehen auch in der Liste stimmt. Fehlt die Migration, verschwindet die Anzeige beim ersten `PGRST202`/`42883` still.
- **Primer: eine Spalte an `decks`, kein eigener Tabellen-Satz:** `deck-primer.service.ts` + `deck-primer/` zeigen und schreiben die selbst verfasste Deck-Beschreibung (`decks.primer`, `sql/deck-primer-2026-09-22.sql`) — in der Deck-Ansicht und im öffentlichen Stöbern als zweiter Reiter neben der Kartenliste (`viewer.deckTab()`), Vorbild Moxfield. Kopfbereich (Name, Format, Bracket) und Kommentare stehen außerhalb des Umschalters und bleiben in beiden Reitern sichtbar. **Es gibt keine neue RLS-Policy und es soll auch keine geben:** Lesen folgt automatisch der Sichtbarkeit des Decks, Schreiben dem bestehenden Update-Recht — eine eigene Tabelle müsste beide Regeln ein zweites Mal nachbauen, und zwei Fassungen derselben Regel laufen auseinander. Für Fremde erscheint der Reiter nur, wenn das Deck einen Primer hat; für den Besitzer immer. `updated_at` bleibt beim Speichern unangetastet — ein Primer sagt etwas *über* das Deck, und ein Tippfehler in der Beschreibung soll kein Deck an die Spitze der nach Datum sortierten Listen heben. Fehlt die Migration noch, schaltet sich der Reiter beim ersten `42703`/`PGRST204` still ab (gleiche Mechanik wie bei den Bracket-Spalten).
- **Primer-Markup: `primer-html.ts` ist die Schranke, nicht die Formatierung:** Geschrieben wird in einem `contenteditable`-Feld (`document.execCommand`, kein Editor-Paket — jedes liefert am Ende dasselbe HTML, das trotzdem bereinigt werden müsste). **Gespeichert wird nie, was im Feld steht:** Eine kurze Positivliste lässt Absätze, Überschriften, Hervorhebungen, Listen, Zitate, `http(s)`/`mailto`-Links, Manasymbole, Kartennamen und Bilder durch; `<script>`, `style`, Ereignis-Attribute und `javascript:`-Ziele kommen gar nicht erst in die Datenbank. Angular bereinigt beim Anzeigen über `[innerHTML]` ein zweites Mal — die erste Schicht schützt die Spalte, die zweite nur die eigene Anzeige, deshalb beide. Dieselbe Datei macht beim Speichern aus drei Kürzeln echtes Markup: `{G}` (und `[G]`, aber nur Farb-/Sondersymbole — `[1]` ist in einem Text öfter eine Fußnote als eine Manakosten-Angabe) wird zum Manasymbol, `[[Sol Ring]]` zum anklickbaren Kartennamen, der die übliche Kartenvorschau öffnet. **Die Symbol-Klasse kommt aus `manaKlasse()` in `ui/mana-symbol/`** — stünde sie hier ein zweites Mal, sähen die Symbole im Primer nach der nächsten Änderung dort anders aus als überall sonst. Kein `loading="lazy"` an den Bildern: Angulars Bereinigung kennt das Attribut nicht und wirft es beim Anzeigen weg. Weil der Inhalt per `innerHTML` hereinkommt, trägt er **kein** Angular-Komponenten-Attribut — die Stilregeln dafür stehen deshalb unter `:host ::ng-deep` (der einzige Ort im Projekt) und greifen sonst nicht. **Der Bearbeiten-Modus zeigt die Kürzel, nicht das Ergebnis** (`primerAlsBearbeitbaresHtml()`, die Gegenrichtung von `bereinigePrimerHtml()`): Ein Manasymbol ist ein Element *ohne* Text — im Schreibfeld ließe sich daran nichts markieren und die Rücktaste träfe es nur zufällig. Deshalb wird beim Öffnen zurückverwandelt (`{G}`, `[[Sol Ring]]`), und auch der Werkzeugkasten fügt das Kürzel ein statt des fertigen Markups; beim Speichern entsteht daraus wieder Symbol und Kartenlink. **Zurück immer in geschweiften Klammern**, auch für Farben: In eckigen gelten nur Farb- und Sondersymbole, `[2]` bliebe beim nächsten Speichern als Text stehen und das Symbol wäre weg. Bilder bleiben dabei Bilder — als Adresse im Text wären sie eine unlesbare Zeile, und ein Bild lässt sich im Schreibfeld ohnehin anklicken und löschen. `primer-html.spec.ts` prüft Schranke, Kürzel und dass ein Primer den Hin- und Rückweg unverändert übersteht.
- **Steckbrief: das Bild IST die Ansicht:** `steckbrief-canvas.ts` + `deck-steckbrief/` zeigen ein Deck als quadratische Karte zum Teilen (Vorbild deckpassport.com) — dritter Reiter neben Deckliste und Primer, in **beiden** Deck-Ansichten (`deck-detail-view`, `public-deck-browser`). Der Reiter zeigt **kein** nachgebautes HTML, sondern das 1080×1080-`<canvas>` selbst; der Download-Knopf speichert genau diese Pixel als PNG. Grund: Eine zweite, in HTML gebaute Vorschau wäre eine zweite Fassung desselben Layouts, und dann lädt jemand etwas anderes herunter, als er angesehen hat. **Gespeichert werden nur zwei Sätze** (`decks.steckbrief_kurz`/`steckbrief_sieg`, `sql/deck-steckbrief-2026-09-22.sql`) — worum es dem Deck geht und woran es gewinnt; alles andere (Commander samt Artwork als Hintergrund, Farben, Bracket, Ø Manawert und die vier Wirkungs-Kacheln Entfernung/Rampe/Kartenziehen/Bretträumung) rechnet die App aus dem ohnehin geladenen Deck. Wie beim Primer **keine eigene Tabelle und keine neue RLS-Policy**: Lesen folgt der Deck-Sichtbarkeit, Schreiben dem Update-Recht. **Der Ø Manawert kommt als Eingabe herein** (`averageCmc()` der jeweiligen Ansicht) statt in der Komponente neu gerechnet zu werden — sonst stünde im geteilten Bild irgendwann etwas anderes als eine Bildschirmhöhe darüber. **Die vier Wirkungszahlen lädt die Komponente dagegen selbst** über `CardDataService.effectCategories()` (eine Abfrage auf `scryfall_card_effects`): Die Deck-Analyse rechnet dieselben Kategorien zwar aus, aber erst beim Aufklappen ihrer Sektion, und das öffentliche Stöbern kennt sie gar nicht. Bewusst **ohne** den Scryfall-Rückfall der Deck-Analyse — der kostet bei kaltem Cache ein Dutzend Anfragen mit Pausen, und ein Steckbrief wird geöffnet, um ein Bild zu sehen; frische Spoiler zählen dort eben nicht mit. Die Kategorie-Schlüssel kommen aus `CARD_EFFECT_FILTERS`, die Beschriftungen sind dieselben `deckView.*`-Keys wie in der Analyse. Bewusst **keine** Kartenzahl, Länder, Kreaturen oder Spielbilanz auf dem Bild: Das steht entweder ohnehin über der Kartenliste oder sagt nichts, was man nicht schon am Commander sieht. **Manasymbole liest der Zeichner aus dem fertigen Stil** (unsichtbares Probe-Element mit `manaKlasse()`, dann `getComputedStyle`) statt aus einer zweiten Zeichentabelle. Kartenbilder müssen über `card-image-datauri.ts` als `data:`-URL hereinkommen (dieselbe Proxy-Regel wie beim PDF-Export) — ein direkt geladenes Fremdbild vergiftet das Canvas und jeder Download endet im `SecurityError`. **Das Bild ist IMMER englisch**, unabhängig von der eingestellten Oberflächensprache (nur die zwei selbst geschriebenen Sätze bleiben, wie sie getippt wurden): Es ist das einzige in dieser App, das sie verlässt — es landet in Beiträgen auf Reddit und Discord, und dort liest es niemand auf Deutsch. Dafür gibt es `I18nService.tIn(lang, key)` neben `t()`; wer im Zeichner `t()` benutzt, macht das Bild wieder zweisprachig. Die Bedienelemente um das Bild herum bleiben dagegen in der App-Sprache — die sieht nur, wer die App benutzt. **Der QR-Code unten rechts** führt auf `?deck=<id>` (siehe Navigation ganz oben) und damit in die öffentliche Deck-Ansicht - wer scannt, ist im Zweifel nicht eingeloggt. Er sitzt auf weißem Grund, weil Kameras einen QR-Code ohne helle Umrandung oft nicht erkennen, und **private Decks bekommen keinen** (`istPrivat`): Der Link liefe für jeden anderen ins Leere, und ein toter QR-Code auf einem Bild zum Teilen ist schlimmer als keiner. Die Adresse kommt aus `window.location.origin` - ein Steckbrief, der auf einer Cloudflare-Preview erzeugt wird, trägt deshalb einen QR auf diese Preview. Abhängigkeiten laufen nur in diese Richtung (Fach-Service → State/Analysis), nie zurück zur Fassade - sonst entsteht ein Zyklus. Jeder Fach-Service hat `reset()`, das `open()`/`close()` aufrufen.
- **CSP und Cache-Header:** `public/_headers` — wer eine neue externe API anbindet, muss sie hier freischalten, sonst blockt der Browser sie stillschweigend.
- **Supabase-Migrationen:** `sql/` (datierte Skripte). **Diese Dateien laufen nicht automatisch** — sie müssen von Hand im Supabase-SQL-Editor ausgeführt werden, ein Merge allein ändert an der Datenbank nichts. Wer einem Fehler nachgeht, der nach „die App speichert nicht“ aussieht, prüft deshalb zuerst die Browser-Konsole: Rechte-Fehler kommen als HTTP 500 mit Postgres-Codes wie `42P17` an, nicht als Code-Fehler (siehe `sql/fix-tournament-rls-recursion-2026-09-03.sql`). **Wenn die Datenbank am 500-MB-Limit des Free-Plans steht:** `sql/datenbankgroesse-pruefen-2026-09-20.sql` zeigt Tabellen- und Indexgrößen, Aufblähung und Zuwachs je Tabelle; **die erste Messung (20.09.2026, 398 MB) steht im Kopf der Datei.** Kurz: Die **echten App-Daten sind 7 MB** (2 %) — der Rest ist Spellbook-Cache (193 MB), ein externer Deckvorrat (110 MB, am 29.09.2026 gelöscht) und Scryfall-Cache (48 MB). Zwei naheliegende Verdächtige sind damit **widerlegt**: Die nächtlichen Abgleiche schreiben zwar jede Nacht alles neu (`spellbook_combos`: 1.377.393 Updates auf 105.025 Zeilen), aber `autovacuum` kommt hinterher — 5,2 % tote Zeilen, nicht 50 %. Und die Indizes sind nicht aufgebläht, sondern teuer entworfen: `spellbook_combo_cards_pkey` ist mit 33 MB fast so groß wie seine Tabelle, weil der Schlüssel `(combo_id text, name_normalized text)` bei 383.229 Zeilen rechnerisch genau so viel kostet. **Das war derselbe Fehler wie beim früheren Deckvorrat** (dort 72 MB nur für den Primärschlüssel) — **behoben am 20.09.2026** durch `sql/spellbook-combo-card-arrays-2026-09-20.sql` (ein Array je Combo statt 3,6 Zeilen).
- **Nächtliche Abgleiche (GitHub Actions):** `scripts/sync-scryfall-bulk.js` (Workflow `scryfall-sync.yml`, füllt `scryfall_cards`/`scryfall_card_effects`, Tabellen in `sql/scryfall-cache-2026-09-06.sql`) und `scripts/sync-spellbook-bracket.js` (Workflow `spellbook-sync.yml`, füllt `spellbook_card_flags`/`spellbook_two_card_combos`, Tabellen in `sql/spellbook-cache-2026-09-06.sql`, sowie `spellbook_combos`/`spellbook_combo_cardlists` samt der Suchfunktion des Combo-Finders, Tabellen in `sql/spellbook-combos-2026-09-07.sql` und — **maßgeblich für die Kartenliste** — `sql/spellbook-combo-card-arrays-2026-09-20.sql`; die Indizes auf `synced_at` ebendort und in `sql/spellbook-sync-cleanup-2026-09-16.sql` — ohne sie liest Postgres beim nächtlichen Aufräumen die ganze Tabelle und der Lauf stirbt an einer Zeitüberschreitung). **Die Kartenliste je Combo ist ein Zahlen-Array, keine Zeile je Karte:** `spellbook_combo_cardlists.card_ids` verweist auf `spellbook_card_names.id`, gefunden wird über den GIN-Index (`&&`). Die frühere Form `spellbook_combo_cards` kostete 82 MB, davon 33 MB allein für den Primärschlüssel `(combo_id text, name_normalized text)` — dieselbe Falle wie beim früheren Deckvorrat. Wer die Kartennamen braucht, `unnest`t `card_ids` und joint auf `spellbook_card_names`). Beide brauchen das Repo-Secret `SUPABASE_SERVICE_ROLE_KEY` und sind über „Actions“ von Hand auslösbar. Sie holen öffentliche Kartendaten einmal pro Nacht von einem Server, statt sie bei jedem Deck-Öffnen aus jedem Browser nachzufragen.
- **Urteil F der Bracket-Einstufung (empirisch):** `src/app/bracket.ts` hebt ein Deck auf mindestens Bracket 4, wenn es eine spielbeendende Combo **und** mindestens N Tutoren enthält (Startwert 2, fortgeschrieben aus `bracket_benchmark`, siehe unten). Das ist das einzige Kriterium dort, das **nicht** aus dem Regelwerk stammt, sondern aus einer Auswertung von 48.638 Decks mit selbst angegebener Stufe (93 % der Decks mit dieser Verbindung nennen sich selbst Bracket 4 oder 5, von Stufe 2 zu Stufe 4 Faktor 30). Die Zahl der Combos liefert die Datenbankfunktion `winning_combos_in_deck` (`sql/winning-combos-in-deck-2026-09-16.sql`, setzt die materialisierte Ansicht `spellbook_winning_combos` voraus, aufgefrischt am Ende des Spellbook-Abgleichs oder von Hand mit `select public.refresh_spellbook_winning_combos();`), aufgerufen von `CardDataService.winningCombosIn()`. Ohne die Funktion kommt 0 zurück und Urteil F hebt nicht an — die Einstufung läuft dann wie vorher.
- **Zwei Sieg-Definitionen, beide nur in SQL:** seit `sql/sieg-definition-breit-2026-09-17.sql` gibt es **eng** (`spellbook_sofort_sieg_muster()`, „beendet das Spiel unmittelbar“) und **weit** (`spellbook_winning_combo_muster()`, „Endpunkt eines Decks“), dazu die Ausschlussliste `spellbook_sieg_ausnahme()`. Urteil F filtert über die enge (Spalte `beendet_sofort` der Ansicht) — die Liste bleibt unverändert, weil die Schwellen daran geeicht wurden. Wer einen Ausdruck ändert: **kein `\b`** — in Postgres ist das ein Rückschritt-Zeichen, keine Wortgrenze.
- **Bracket-Benchmark, lernt aus eigenen Decks:** `docs/bracket-benchmark-2026-09.md` hält die Ausgangsauswertung fest (48.638 Decks einer externen Stichprobe mit selbst angegebener Stufe, **nur Kennzahlen**): Trennschärfe (AUC) je Merkmal (Game Changer 0,898, Tutoren 0,771, alles Simulierte im Rauschen), Grundlage von Urteil F, Sieg-Definition, Methode. **Goldfish-Stapelsimulation, der externe Deckvorrat und die Legalitätsprüfung sind am 29.09.2026 komplett entfernt worden** (Code, Workflows, Tabellen): Simulierte Merkmale trennen die Stufen nicht, und fremde Deckdaten sollen nicht in einer App liegen, die vermarktet wird. **Nicht wieder aufbauen, ohne das Dokument gelesen zu haben.** **Seit dem 29.09.2026 schreibt die App den Benchmark selbst fort** (`sql/bracket-benchmark-2026-09-29.sql`): `bracket_benchmark_aktualisieren()` misst am Ende des Spellbook-Nachtlaufs jedes Commander-Deck mit **selbst gewähltem** `decks.bracket` (auch private; je Deck nur fünf Zahlen in `bracket_benchmark_decks`, für Clients unlesbar) und schreibt je Bracket die Mediane nach `bracket_benchmark` — **erst ab 100 Decks dieses Brackets**, darunter bleiben die Startwerte (= die früheren festen Werte). Gelernt werden nur die nicht-offiziellen Teile: Tuning-Spannen (Median B2 → Median B5, nicht B4, sonst bekäme jedes zweite B4-Deck den cEDH-Hinweis) und die Tutorenschwelle von Urteil F (`combo_tutor_min`, erst wenn B2, B3 und B4 je 100 Decks haben). **Der Tuning-Grad ist ein gewichtetes Mittel** (`BracketBenchmark.weights`): Gewicht = Trennschärfe |AUC − 0,5| zwischen B2 und B4, Startwerte aus dem Benchmark-Dokument (Game Changer 0,40, Tutoren 0,27, ungetappte Länder 0,16, Ø Manawert 0,13; **die App liest den Game-Changer-Teil seit 05.10.2026 nicht mehr**, siehe Deck-Check - der Nachtlauf misst ihn unverändert weiter), gelernt von `bracket_benchmark_gewichte()` (`sql/bracket-gewichte-2026-09-29.sql`, Spalten `weight_*` in der Zeile von B4, erst ab je 100 Decks in B2 und B4, aufgerufen im Spellbook-Nachtlauf). Die Anhebe-Schwelle `TUNING_BUMP_SCHWELLE` ist dafür von 0,8 auf 0,7 gesunken - gewichtet erreicht ein B3-Deck (höchstens drei Game Changer) sonst nie mehr die Schwelle. Die App liest das über `CardDataService.bracketBenchmark()` → `BracketBenchmark` in `bracket.ts` (`DEFAULT_BRACKET_BENCHMARK` ohne Migration). **Die Merkmale stehen zweimal** (SQL-Funktion und `deck-analysis.service.ts`) — wer die Messung ändert, ändert beide.
- **Generiert, niemals von Hand anfassen:** `src/app/version.ts` (erzeugt von `scripts/generate-version.js` bei jedem `start`/`build`, gitignored)

### Die Karte mitpflegen

Die Architektur-Karte oben ist nur so lange etwas wert, wie sie stimmt. **Eine falsche Karte ist schlimmer als gar keine** — sie schickt die nächste Session gezielt an den falschen Ort. Das ist schon passiert: Die Karte entstand in PR #164 und war vier Commits später falsch, weil die i18n-Aufteilung sie nicht mitzog; die Korrektur brauchte einen eigenen PR (#167).

**Wer eine Datei anlegt, löscht oder umbenennt, die in die Karte gehört, aktualisiert die Karte im selben PR.** Das betrifft:

| Was du änderst                        | Was in der Karte nachgezogen wird                    |
| ------------------------------------- | ---------------------------------------------------- |
| Komponente unter `src/app/`           | Komponenten-Tabelle                                  |
| Service/Helper flach in `src/app/`    | Services-Tabelle                                     |

Ein PR, der die Struktur ändert und die Karte stehen lässt, ist unvollständig — genauso wie ein i18n-Key, den es nur auf Deutsch gibt.

`npm run check:map` sagt dir, was fehlt. Wichtig zur Einordnung:

## Test-Accounts: die App selbst anschauen und Änderungen validieren

Die App läuft lokal gegen die **Produktiv**-Supabase. Damit kann jede Session die laufende App
selbst bedienen — einloggen, durchklicken, Screenshots machen — statt Änderungen nur im Code zu prüfen.

**Es gibt keine festen Testkonten mehr.** Die früheren vier Konten der „Claude Testgruppe" wurden
am 23.09.2026 zusammen mit rund 30 liegengebliebenen Wegwerfkonten gelöscht
(`sql/konten-aufraeumen-2026-09-23.sql`). Die Registrierung ist offen und `mailer_autoconfirm` ist
aktiv, ein frisches Konto ist also in Sekunden einsatzbereit. Wer eines braucht:

- **E-Mail immer nach dem Muster `claude.<zweck>.<zeitstempel>@example.com`** — nur so erkennt
  das Aufräum-Skript das Konto später wieder. Ein Konto unter anderem Namen bleibt für immer liegen
  und landet in der Kontenliste des Users.
- **Nie in eine echte Gruppe eintreten** und keine Partien in einer echten Gruppe speichern — das
  Aufräum-Skript bricht dann ab, statt echte Partien mitzulöschen. Für Statistik-Ansichten eine
  eigene Gruppe anlegen und dort ein paar Matches spielen.
- **Ein Konto je Session reicht.** Nach dem Test nicht selbst löschen (die Session hat keinen
  Service-Key); der User lässt `sql/konten-aufraeumen-2026-09-23.sql` bei Gelegenheit erneut laufen.

### Erwartung an neue Sessions

Wer die UI ändert, prüft die Änderung **in der laufenden App** und belegt sie mit einem
Screenshot — nicht nur mit `npm run typecheck`. Das Projekt hat kein Lint, keine Build-CI und
praktisch keine Tests; der Screenshot ist der einzige echte Nachweis.

### So geht es

`npm start` (Dev-Server auf `localhost:4200`, spricht mit der Produktiv-Supabase), dann
Playwright 1.56 und Chromium — beide sind in der Umgebung vorinstalliert, **kein**
`playwright install`:

```js
const browser = await chromium.launch({
  executablePath: '/opt/pw-browsers/chromium',
  args: [
    '--no-sandbox',
    '--disable-quic',
    '--disable-features=PostQuantumKyber,TLS13KyberSupport,EncryptedClientHello,UseDnsHttpsSvcb',
    '--ssl-version-max=tls1.2',
  ],
});
const ctx = await browser.newContext({ viewport: { width: 390, height: 844 }, isMobile: true, locale: 'de-DE' });
```

Vier Stolpersteine, die sonst jede Session neu sucht:

1. **Keine `proxy:`-Option setzen.** Chromium übernimmt den Proxy aus der Umgebung, und
   `no_proxy` nimmt `localhost` bereits aus. Eine explizite Proxy-Option schickt auch die
   Anfragen an `localhost:4200` in den Proxy — die App lädt dann gar nicht.
2. **Die TLS-Flags oben sind Pflicht.** Ohne sie bricht der Tunnel zu Supabase mit
   `ERR_CONNECTION_RESET` ab; der Post-Quantum-ClientHello ist dem Proxy zu groß.
3. **Das Tutorial startet nicht mehr von selbst** (seit 30.09.2026) — nur über das Fragezeichen
   in der Kopfzeile (`.help-toggle`) bzw. „Tracker erklären“ im ⋮-Menü des Live-Trackers. Solange
   es offen ist, fängt es alle Klicks ab; „Schließen“ (erster Knopf im `.tutorial-tooltip`) beendet es.
4. **Stabile Selektoren:** Tabs tragen `data-tutorial="nav-match|search|stats|group|profile"`,
   Dialoge liegen in `.options-menu-sheet`, Bestätigungen in `app-dialog` (Button `.primary`).

Ablauf für Matches (erzeugt Statistiken): Match-Tab → Spieler-Chips wählen → je Spieler
„📚 Deck wählen" → „▶ Spiel starten" → im Tracker ⋮ → „🏁 Spiel beenden" → Sieger 🏆 →
„Match speichern & beenden" → den `app-dialog` bestätigen.
